# GitHub Workflow Labels

This document defines the label taxonomy used for organizing issues and PRs.

## Label Taxonomy

### Type Labels
- `type:feature` - New feature or functionality
- `type:bug` - Bug report or fix
- `type:docs` - Documentation changes
- `type:test` - Test additions or improvements
- `type:chore` - Maintenance, dependencies, build
- `type:refactor` - Code refactoring without functional changes

### Area Labels
- `area:backend` - Backend/API changes
- `area:frontend` - Frontend/UI changes
- `area:ci` - CI/CD and GitHub Actions
- `area:docs` - Documentation
- `area:data-catalog` - Data platform concepts
- `area:devops` - Infrastructure and deployment

### Priority Labels
- `priority:high` - Critical, must fix soon
- `priority:medium` - Important but not urgent
- `priority:low` - Nice to have, can defer

### Status Labels
- `status:needs-triage` - Needs review to categorize
- `status:needs-clarification` - Awaiting more information
- `status:blocked` - Blocked by another issue
- `status:needs-review` - Awaiting code review
- `status:in-progress` - Currently being worked on
- `status:ready-to-merge` - Approved and ready

### Community Labels
- `good first issue` - Great for new contributors
- `help wanted` - Contributions welcome
- `question` - Question or discussion

---

## Usage Guidelines

- **Every issue should have at least one `type:` label**
- **Most issues need at least one `area:` label**
- **Use `priority:` labels for prioritization**
- **Use `status:` labels to track workflow progress**
